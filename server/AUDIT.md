# Central operational Audit Log

Runway/Maestro: open **RPA → Audit Log**, supply the administrative API key for that page session, then **Apply / Refresh**. Assets and Audit are centralized Runway management features. Studio consumes Asset references in activities and selects the execution environment; it does not host these management panels.

The timeline combines Asset/environment mutations, Human Task creation/wait/approval/rejection/timeout/cancellation, operator administration/token rotation, and newly observed Robot Job status changes/submissions. Existing Human Task and Asset audit rows are imported idempotently on first access. Historical Asset actors were not recorded and are labelled `unknown:legacy`; they are never inferred from the current viewer. This does not audit unrelated Maestro routes or distribution/portal administration.

Filter by exact user identity (suggestions include `user:<operator-id>`), operation, source, and local start/end date/time. Start is inclusive; end is exclusive. Requests convert dates to UTC epoch milliseconds. Refresh starts a new snapshot; Load more uses stable timestamp/ID pagination within that snapshot. New events appear after Refresh.

Audit reads require the administrative API key and are tenant scoped. An optional **personal task token** verifies individual identity. Apply a valid token in Runway Audit before editing Runway Assets to attribute those edits to `user:<id>`. Tokens live only in module/session memory, scoped to the Maestro connection and tenant; changing the token clears the previous attribution until successfully verified. Clear the token and Apply to return to shared-key identity. Human Task decisions always use their verified personal identity. Shared API key actions appear as `admin:shared-key` because a shared key cannot prove which person used it. Robot events use the registered Robot ID; internal task timers use a system identity. Arbitrary user headers and published names are not identity evidence.

Central records contain time, identity, source, operation, target IDs, outcome, optional environment/job IDs, and explicitly allowed revision/count/enum metadata. Request/response bodies, Asset values, usernames/passwords, encryption material, token values/hashes, logs, error bodies, Human Task form answers/context and freeform comments are excluded. Identifiers such as Asset names remain visible; do not use secrets as identifiers. Historical Human Task comments are not copied to central audit; existing business records and legacy tables are not erased. New legacy audit writes also omit comments.

Successful source mutations and their new audit rows share a SQLite transaction. Audit insertion failure rolls back the mutation. UPDATE and DELETE of central events are blocked by SQLite triggers. This is application-level append-only storage, not cryptographic tamper evidence against a database administrator. Failed authentication/validation requests are not retained as operational success events. No automatic retention deletion is applied.

Install with `node server/install-maestro-robot-jobs.cjs <Maestro checkout> --update` after reviewing existing adapter differences, then rebuild/restart Maestro. The installer copies the backend and shared UI and adds the RPA tab; packaged backends must include `maestro_audit` (PyInstaller hidden import). Keep the existing Maestro data directory when restarting.

Validation: `node tests/audit/launch.cjs`, `node tests/human-tasks/launch.cjs`, `node tests/assets/launch.cjs`, and the Robot Jobs integration fixture with `--human-tasks --assets --queues --transaction-scope --maestro-source=<script_server.py snapshot>`. All fixtures use temporary profiles/databases and never edit user workflows.
